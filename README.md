# AWS Billing to Microsoft Teams

A small AWS Lambda application that polls AWS Cost Explorer and sends a concise billing summary and service-level breakdown to a Microsoft Teams webhook (Adaptive Card). The function can query multiple AWS accounts and aggregate or report per-account usage.

This README was generated by analyzing the repository's source files (handler.py, serverless.yml, Pipfile, examples) and describes how to configure, deploy and run the project.

Purpose

This project queries AWS Cost Explorer for recent billing data and posts a human-friendly report to a Microsoft Teams webhook. It supports:

- Per-account Cost Explorer queries using explicit AWS credentials for each account
- Customizable reporting window (days), grouping (SERVICE, LINKED_ACCOUNT, etc.), and aggregation metric (UnblendedCost, BlendedCost, ...)
- Monthly overview and a per-service sparkline for recent days
- Optional AWS credits budgeting to annotate cost summaries


Architecture & flow

1. Lambda entrypoint: handler.lambda_handler -> run()
2. run() reads configuration from environment variables and loads the configured AWS accounts.
3. For each account:
   - A boto3.Session is created using the account's credentials.
   - Cost Explorer (ce) is queried for daily and monthly usage data.
   - A textual report and a summary are generated (sparkline, deltas, totals).
   - An Adaptive Card payload is assembled and POSTed to the configured Teams webhook URL.
4. If any account fails, the Lambda raises a RuntimeError listing failed accounts (causing a failing invocation).

Key files

- handler.py - main application logic (loading env, talking to Cost Explorer, creating payload, sending to Teams)
- serverless.yml - Serverless configuration to deploy the Lambda (IAM permissions, schedule, environment defaults)
- Pipfile / Pipfile.lock - Python dependencies (boto3, requests, python-dotenv)

Requirements & dependencies

- Python 3.10 (project Pipfile sets python_version = "3.10")
- Python packages (see Pipfile / Pipfile.lock):
  - boto3
  - requests
  - python-dotenv (optional, used when present to load a local .env file)

- Serverless Framework for deploying the function
  - serverless (npm package)
  - serverless-python-requirements plugin (installed as a Serverless plugin)

IAM permissions required by the Lambda (declared in serverless.yml):
- ce:GetCostAndUsage
- iam:ListAccountAliases


Configuration (environment variables)

The function is configured via environment variables. The most important variables are:

- TEAMS_WEBHOOK_URL (required) — Microsoft Teams incoming webhook to send Adaptive Card payloads.

Reporting options:
- GROUP_BY (default: SERVICE) — dimension to group by (SERVICE, LINKED_ACCOUNT, REGION, etc.)
- LENGTH (default: 5 in code, serverless.yml sets 10) — how many top services to include in the visible list
- REPORT_DAYS (default: 7) — number of days to include for daily sparkline and per-day breakdown
- COST_AGGREGATION (default: UnblendedCost) — which cost metric to use; values: AmortizedCost, BlendedCost, NetAmortizedCost, NetUnblendedCost, NormalizedUsageAmount, UnblendedCost, UsageQuantity
- BILLING_END_DATE (optional) — YYYY-MM-DD string to use as the report end date (useful for backfills or testing)

AWS accounts configuration

This project supports multiple AWS accounts by reading explicit credential sets from environment variables. The handler expects an integer count and per-account sets named with a common prefix:

- AWS_ACCOUNT_COUNT — total number of accounts you will configure (positive integer)

For each account i (1..AWS_ACCOUNT_COUNT), the following environment variables are required:
- AWS_ACCOUNT_i_NAME — a friendly name for the account (string)
- AWS_ACCOUNT_i_ACCESS_KEY_ID — AWS access key id
- AWS_ACCOUNT_i_SECRET_ACCESS_KEY — AWS secret access key
- AWS_ACCOUNT_i_REGION — optional; falls back to AWS_REGION or us-east-1
- AWS_ACCOUNT_i_SESSION_TOKEN — optional (if using temporary credentials)

Note: AWS_REGION (or AWS_DEFAULT_REGION) can be provided as a default region used when per-account REGION is not present.


Deploying with Serverless

1. Install serverless (Node/npm):

   npm install -g serverless

2. Install the Serverless Python requirements plugin (once per project):

   serverless plugin install -n serverless-python-requirements

3. Install Python dependencies (recommended using pipenv):

   pip install pipenv==2023.7.4
   pipenv install --dev

4. Provide environment variables when deploying. Serverless supports passing parameters which are substituted into serverless.yml, or you can set real environment variables in your CI/CD system or Serverless dashboard.

Basic deploy example (replace TEAMS webhook and account variables):

   serverless deploy --stage="prod" --param="teams_url=https://outlook.office.com/webhook/XXX/IncomingWebhook/YYY/ZZZ"

However, because this project expects multiple AWS account credentials, you will typically supply secrets via a secure mechanism (see "Security notes"). For a quick test you can set the environment variables locally and then deploy/invoke.

Invoke once (to test) with all required variables present in your environment:

   serverless invoke --function report_cost --stage="prod"

Running locally

To run the script locally for testing you can set environment variables and execute handler.py directly:

1. Create a .env file (optional) with the required environment variables, for example:

   AWS_ACCOUNT_COUNT=1
   AWS_ACCOUNT_1_NAME=MyAccount
   AWS_ACCOUNT_1_ACCESS_KEY_ID=AKIA...
   AWS_ACCOUNT_1_SECRET_ACCESS_KEY=...
   AWS_ACCOUNT_1_REGION=us-east-1
   TEAMS_WEBHOOK_URL=https://outlook.office.com/webhook/...

2. Run the handler as a script:

   python handler.py

This will perform the same actions as the Lambda handler: query Cost Explorer for each configured account and POST the Adaptive Card to the Teams webhook.

Important: Ensure the AWS credentials you set have permission to call Cost Explorer (ce:GetCostAndUsage) in the account being queried. Cost Explorer is a global service but the handler uses the region us-east-1 for Cost Explorer calls by default.

Example outputs

- The function prints a textual table to stdout containing the top services, yesterday's cost, the percent delta vs the previous day, and a sparkline for the configured REPORT_DAYS.
- The Teams payload is an Adaptive Card containing:
  - Current month total
  - Forecasted month-end value (or run-rate estimate if AWS forecast is unavailable)
  - A per-service table with yesterday, change and the sparkline

See example_boto3_result.json and example_boto3_result2.json for sample Cost Explorer responses used in development.

Troubleshooting

- If the function raises DataUnavailableException from Cost Explorer, the handler will fall back to generating a zero-cost report for the period and still publish a card.
- If no TEAMS_WEBHOOK_URL is provided the application will raise an error when run (TEAMS_WEBHOOK_URL is required by the code path that posts notifications).
- If you see authentication errors, verify that the per-account AWS credentials are correct, active, and have the required Cost Explorer permissions.
- If forecasts are unavailable, the handler falls back to a run-rate estimate and logs the reason to stderr.

Security notes

- Do NOT commit AWS keys or webhook URLs into source control. Use your CI/CD system's secret store, AWS Systems Manager Parameter Store, or AWS Secrets Manager and reference those values at deploy time.
- Prefer using cross-account roles and temporary credentials over long-lived access key/secret pairs when possible.

Adding a New AWS Account

To add a new user or AWS account to this application, you must update the environment variables as follows:
1. Update the `AWS_ACCOUNT_COUNT` variable to reflect the new total number of accounts.
2. Add a new alias variable for the account: `AWS_ACCOUNT_X_NAME` (Replace 'X' with the new account's sequence number, e.g., 2, 3, 4, etc.).
3. Add the following credential variables for the new account, making sure to replace 'X' with the same sequence number used above:
   - `AWS_ACCOUNT_X_ACCESS_KEY_ID`
   - `AWS_ACCOUNT_X_SECRET_ACCESS_KEY`
   - `AWS_ACCOUNT_X_REGION`

(Optionally add `AWS_ACCOUNT_X_SESSION_TOKEN` if you use temporary credentials.)
